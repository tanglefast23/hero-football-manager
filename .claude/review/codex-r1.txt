The revised spec is directionally sound, but it is not safe to implement yet. Two contradictions can break English or existing saves, followed by several high-risk gaps.

1. **BLOCKER — The English catalog has no implementable source format.** The runtime API retains only a key—`t('creation.stat.pac.label')`—while the spec says English remains authored “at the call site” and `en.json` is generated from those call sites ([spec §3.2–3.3](/Users/joemacprom5/Documents/Vibecode/Hero_Football_Manager/.claude/worktrees/multilingual-copy-translation-bbe9c8/docs/superpowers/specs/2026-08-06-multilingual-copy-design.md:165)). Once the literal is replaced by that key, there is nothing from which to regenerate English. The ledger example also removes `label` ([spec line 102](/Users/joemacprom5/Documents/Vibecode/Hero_Football_Manager/.claude/worktrees/multilingual-copy-translation-bbe9c8/docs/superpowers/specs/2026-08-06-multilingual-copy-design.md:102)), contradicting the later mandatory dual-write rule. Define a concrete authoring primitive such as `defineCopy(key, english)` or a hand-authored TS English-source registry, then generate JSON from that. Without this, the English snapshot and no-regression promise cannot work.

2. **BLOCKER — The no-`GAME_SCHEMA_VERSION` conclusion does not cover the proposed `cupResult` shape change.** The spec says `seasonRecap.cupResult` becomes `{ outcome, round }`, then says no game-schema bump is required ([spec lines 443–468](/Users/joemacprom5/Documents/Vibecode/Hero_Football_Manager/.claude/worktrees/multilingual-copy-translation-bbe9c8/docs/superpowers/specs/2026-08-06-multilingual-copy-design.md:443)). Today the codec requires a string ([game-state-codec.ts:1163](/Users/joemacprom5/Documents/Vibecode/Hero_Football_Manager/.claude/worktrees/multilingual-copy-translation-bbe9c8/src/persistence/game-state-codec.ts:1163)). Replacing it with an object breaks every old recap. Either retain required English `cupResult` and add optional semantic fields, or bump to schema 6 with an explicit migration. The optional-field/no-bump reasoning is valid only for genuinely optional additions.

3. **HIGH — One persisted “copy” field is also parsed as game data.** `hall-of-fame.ts` extracts goals only from exact English matching `^(\d+) goals$` and silently returns zero otherwise ([hall-of-fame.ts:50](/Users/joemacprom5/Documents/Vibecode/Hero_Football_Manager/.claude/worktrees/multilingual-copy-translation-bbe9c8/src/application/hall-of-fame.ts:50), [consumer at line 326](/Users/joemacprom5/Documents/Vibecode/Hero_Football_Manager/.claude/worktrees/multilingual-copy-translation-bbe9c8/src/application/hall-of-fame.ts:326)). That string is authored in the recap builder ([season-recap.ts:87](/Users/joemacprom5/Documents/Vibecode/Hero_Football_Manager/.claude/worktrees/multilingual-copy-translation-bbe9c8/src/game/season-recap.ts:87)). Store an optional numeric `goals` field and use the regex only for legacy saves. Otherwise a harmless English rewrite can corrupt Hall of Fame totals. The eleven-surface inventory is otherwise substantially complete, although persisted Cup round labels remain English-valued enum tokens ([game-state-codec.ts:916](/Users/joemacprom5/Documents/Vibecode/Hero_Football_Manager/.claude/worktrees/multilingual-copy-translation-bbe9c8/src/persistence/game-state-codec.ts:916)); keep those as stable IDs and translate only at presentation.

4. **HIGH — The preferences migration can reset real users’ settings while tests still pass.** Versions 3–8 are derived from the current `PreferencesSchema` using `.omit()` ([preferences-repository.ts:88](/Users/joemacprom5/Documents/Vibecode/Hero_Football_Manager/.claude/worktrees/multilingual-copy-translation-bbe9c8/src/persistence/preferences-repository.ts:88), [legacy schemas at line 129](/Users/joemacprom5/Documents/Vibecode/Hero_Football_Manager/.claude/worktrees/multilingual-copy-translation-bbe9c8/src/persistence/preferences-repository.ts:129)). Adding required `language` to that base makes those legacy schemas require a field old rows do not contain. Worse, several migration tests construct old fixtures from `DEFAULT_APP_PREFERENCES`, so they will accidentally acquire `language` and mask the failure ([preferences tests:79](/Users/joemacprom5/Documents/Vibecode/Hero_Football_Manager/.claude/worktrees/multilingual-copy-translation-bbe9c8/src/persistence/__tests__/preferences-repository.test.ts:79)). Freeze an explicit V9 schema, extend it for V10, add a literal version-9 fixture without language, and verify literal fixtures for every version 1–9. Failure currently resets all settings through the fail-soft path ([preferences.ts:24](/Users/joemacprom5/Documents/Vibecode/Hero_Football_Manager/.claude/worktrees/multilingual-copy-translation-bbe9c8/src/application/preferences.ts:24)).

5. **HIGH — `vars()` is viable, but the hardcoded-font inventory still misses three major player-facing modules.** NativeWind documents `vars()` as inherited and reactive, so the className mechanism is credible on native ([NativeWind documentation](https://www.nativewind.dev/docs/api/vars)). Replace the literal-count checklist with an AST or resolved-reference gate requiring zero production Silkscreen assignments outside the loader/config allowlist.

Current code explicitly relies on that flexible column paying for every fixed-width increase ([squad-register-columns.ts:96](/Users/joemacprom5/Documents/Vibecode/Hero_Football_Manager/.claude/worktrees/multilingual-copy-translation-bbe9c8/src/ui/squad-register-columns.ts:96)); the full league table already has seven non-shrinking columns ([LeagueTableScreen.tsx:40](/Users/joemacprom5/Documents/Vibecode/Hero_Football_Manager/.claude/worktrees/multilingual-copy-translation-bbe9c8/src/ui/screens/LeagueTableScreen.tsx:40)). Because widths are global maxima, rerun English visual/layout acceptance after each locale is enabled—or calculate the final seven-locale maxima before Phase 2—so German/Vietnamese cannot regress English later.
